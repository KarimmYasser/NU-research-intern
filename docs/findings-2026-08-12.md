# Agent Architecture Findings — 2026-08-12

Summary of engineering decisions, bugs found, and fixes applied during this session.
Covers the generalization work, file-patching capability, and the architecture bug-triage pass.

---

## 1. Bugs Found & Fixed

### 1a. `fluid_species` and `file_overrides` had no LLM channel

**Problem.** Both `fluid_species` (added to `CaseIntent`) and `file_overrides` (added to
`CaseGraphState`) were wired into the Python side but were absent from the LLM's JSON schema
in `pipeline.py`. The LLM had no structural mechanism to emit either field — they would always
be `None`/absent at runtime regardless of what the model tried to produce.

**Fix.** Added both to `_SCHEMA` (natural-language description) and `_RESPONSE_FORMAT` (JSON
schema grammar) in `pipeline.py`. `fluid_species` is an enum:
`["air", "nitrogen", "co2", "oxygen", "helium", "water_vapour"]`.

For `file_overrides`, a dedicated second LLM call with its own schema was added:
`extract_file_patches()` + `_PATCH_RESPONSE_FORMAT`. This is called by the `patch_files` graph
node rather than being embedded in the intent schema, because mixing physics intent with raw
file content in one call degrades both.

---

### 1b. Stale `file_overrides` surviving across retries

**Problem.** When attempt N puts patches in `file_overrides`, attempt N+1's `render_case`
re-renders the spec from scratch (overwriting the patched files), then re-applies the *same*
stale patches from the previous attempt. Any new patches produced in N+1 could not update the
state.

**Fix.** `build_intent` now returns `{"file_overrides": None}` explicitly, clearing the stale
patches before each fresh render.

---

### 1c. Two retry loops stacked without coordination

**Problem.** `pipeline.py::extract_intent()` has its own 3-attempt loop for JSON parsing failures.
If this loop exhausts itself, it raises — the graph's retry loop never sees a structured error,
just an exception. These two loops are stacked but not coordinated.

**Status.** Not changed — the inner loop is a low-level LLM-output repair loop (strip fences,
isolate JSON span, fix trailing commas) and rarely fires for structurally simple reasons.
The important thing is that Pydantic validation errors from the *wrong physics* are propagated
correctly, which they are (they reach the outer graph loop). This is acceptable technical debt
to note but not fix now.

---

### 1d. `KnowledgeRetriever()` re-instantiated on every `intent_to_spec()` call

**Problem.** `intent_to_spec()` created two fresh `KnowledgeRetriever()` instances per call,
each reading JSON knowledge files from disk. On a 3-attempt run this means 6 disk reads of
the same files.

**Fix.** Added a module-level `_RETRIEVER = KnowledgeRetriever()` singleton in `intent.py`.
Both call sites replaced.

## 2. Architecture: the `patch_files` Node

### What it is

A new LangGraph node activated specifically when `FailureClass.DICTIONARY_SYNTAX` is detected.
Instead of re-running the full `build_intent → expand_spec → render_case` pipeline (which would
discard a potentially good intent), `patch_files`:

1. Reads the content of every file named in the validation errors (via `_collect_file_context`)
2. Calls `extract_file_patches()` — a second, separate LLM call with a different schema
3. The LLM returns `{"file_overrides": {"system/fvSolution": "<corrected full content>", ...}}`
4. These overrides are stored in state and applied by the next `render_case` invocation

### Why a separate LLM call (not one combined schema)

Combining physics-intent fields with raw file content in one schema creates a mixed-mode
extraction problem: the model must simultaneously reason about high-level physics decisions
*and* produce verbatim OpenFOAM dictionary text. Keeping them in separate calls with separate
system prompts lets each call be well-posed.

### Routing rationale

```
DICTIONARY_SYNTAX → patch_files   (targeted keyword fix; renderer has coverage gaps)
ENVIRONMENT       → END           (infra failure; nothing the agent can do)
MESH_*/SOLVER_*   → build_intent  (full intent re-extraction with error in context)
```

The key insight: `DICTIONARY_SYNTAX` in practice is often a *renderer coverage gap* (e.g.
`alphatJayatillekeWallFunction` needed `compressible::alphatJayatillekeWallFunction`), not a
structurally broken file. These are fixable by targeted keyword replacement. A full intent
re-extraction is both slower and less precise — the model would have to re-infer the entire
physics setup to fix one keyword.

## 3. `generate()` Deprecation

`pipeline.py::generate()` is now marked `DeprecationWarning`. It is a legacy single-shot path
that:
- Does not run the `patch_files` node
- Does not clear stale file overrides between retries
- Is not called by the CLI or the graph

Use `orchestration.graph.run()` for all production usage.
